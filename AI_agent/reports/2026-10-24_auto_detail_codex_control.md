# 幸福中心自动细度试跑与 Codex 通用运行对照

本轮已结束。两个新增样本均使用 `gpt-6.1-sol/high`、同一组原始输入、同一最终 materialized source BIM 出口，且没有人工追加建模提示或改交付原件。产品保持 `runtime-v42-20261023 / domain-v146-20261024`，实验源码冻结于 `b77ef64672ad31dddc896cbea311a4bcdae36a51`；本次只更新交接，不发布桌面或修改默认策略。

## 已讨论清楚的设计原则

- 粗档对应最低可接受质量，允许简化是为了节省额外工作；已经识读、推断且能低成本表达的正确内容应保留，不为粗而粗、不先精细生成再删减。
- 细度由局部证据、建筑用途与关系、额外工作的价值共同决定。未知部分仍需合理补足必要功能和通达，已有图纸的开放空间不应被虚构隔断。
- 判断主要交给模型，后续可由空间能力较强的调度员承担。初期采用原则提示和案例，逐步积累反例；固定返工次数不能定义质量档位。
- 上述原则面向所有输入方式。本轮只试验 textured mesh＋图纸＋文字这一输入组合，未宣称已覆盖其他方法。
- 当前采用自动细度做试验；产品是否保留两个用户档位或仅自动，尚未决定。没有新增档位控件或默认验收策略。

## 建筑质量：有不同取舍，不能由文件合法性代替

三份原件均通过相同中性 schema/hash、引用、接触、开口宿主和连接一致性检查。Codex 证明了它可以不依靠本项目生成兼容 BIM，不能把“能输出这个格式”本身当作 harness 的独占收益。

独立查看原图、F05 空间/开口图、六个轮廓截面、竖向截面和立面/体量图后：

- 两组都识别并表达主要外形、两核心、两楼梯、四客梯及消防梯、男女卫生间。Codex 的裙楼过渡形体更贴近参考；自动细度 harness 的标准层窗带匹配更好。两者都未达到或宣称施工图精度。
- Codex 的 `F05_RISER_E` 到 `F12_RISER_E` 每层均有实体底/顶盖；七个层间截面各约 1.1823 m² 被封堵。两部楼梯和五部梯井连续性所检项通过，不能把问题泛化成核心筒全部不通。

## 评价侧的修正也保留

旧共同评价脚本假定 harness 的 `run/bim/candidate` 布局和同目录 display 文件，因此控制组第一版 observer 的几何/拓扑读路径失败。原记录在 `evaluation/control/`；第二版仅在评价目录放原件字节一致的副本与已生成的只读 display projection，复用原测量代码，未伪造 receipt 或改源。

旧语义选择器还因合法 ID `L1/L2/L3/L4/LF` 而错记“0 个电梯”，并漏掉其通达检查。这不是模型漏建。第三版显式记录原图、空间位置、开口和模型说明支持的五个身份，对三臂统一重测同一断言；控制组通达为 72/72，七处管井封盖保持。原错误结果保留，不把命名适配错误混进能力结论。

访问审计检查了完整命令、工具代码和生成脚本，未发现读取本项目、历史答案、MCP、委派或联网抓取建筑答案。初始上下文不含 memory/技能目录；两条 user-role 记录分别是自动环境说明和唯一建模任务。Windows 完整 OS 读隔离没有建立，不能声称内核级完备访问证明；这一限制见控制组报告。

## 下一步判断

当前证据支持保留“依据输入自动判断细度、充分使用已知信息”的方向，但不足以把这版提示提升为默认行为，或证明现有 harness 复杂度有足够的净收益。

下一次讨论应围绕三个具体对象：必要的建筑/拓扑约束带来什么质量收益；哪些提示、工具包装和检查往返可以削减；两条订阅接入的缓存回执差异来自哪里。可考虑以后用相同通用执行底座搭配最小领域约束做进一步对照，但本轮没有自动启动新实验、改造 harness 或诊断 6 Sol 利苑。
