# Textured mesh 方法调研

**当前定位（2026-10-19）：** 下一轮独立搭建mesh入口、方法和验收，共享runtime及通用BIM，局部平面、草图和文字从设计起纳入；由最高调度员自主判断输入用途、精度及worker/工具调用。整体外几何与外窗优先，未知内部合理即可，先用完整贴图案例，不要求外部缺失补全。公共机制需支持立面匹配、非正交/曲线与跨层变化。完整共识见[当前交接](../reports/2026-10-19_textured_mesh_harness_closeout.md)。下文按日期保留旧调研，固定细度、门位、角色或步骤的旧建议不作为当前默认要求。

2026-09-10。当前从“已有三维几何 + 图片贴图”开展部分推理建模，允许局部图纸和文字补充；参考图片等主要靠整体推断的任务归完全推理建模，分类按信息充分程度，不按文件模态。缺信息可在生成过程中交互补足，与 BIM 停点编辑分开。相关目标见 [产品目标](../project/goal.md)，并行工作安排见 [研究计划](../project/partial_inference_research_plan.md)，实际素材见 [案例库](../../case_tests/textured_mass/README.md)。

## 研究对象与产品目的（用户后续确认）

目的是改善前期仿真输入，研究对象是办公、住宿、普通商业等类型化**单体建筑，不考虑周边环境建模**。城市尺度仅是问题背景。复杂公共建筑不是近期主要对象，后续特化或明确简化。类型化也允许混合用途和局部变化，不能将全楼强套同一标准层。

**用户在生成前决定通用轻量 BIM 的复杂度，生成不以选择模拟目的或后端插件为前提。** 先交付由逻辑闭合空间块组成的共同模型，再由用户选择不同模拟插件；后端可以继续调整模型、合并热区等。当前只梳理简化/合并方向，档数、控件、各档对应关系及具体算法后续详细设计。复杂度不等于实测准确性，也不定义任务属于哪类建模。当前已整理研究计划，尚未开展新生成实验。

## 用户获取输入与现有模拟实践

**09-18 用户确认素材责任划分：当前主要是在开发阶段摸出一条可行的路，产品投入使用后，素材由用户自己去找所需的建筑贴图模型。** 因此开发侧不需要解决「全球任意建筑都能取到」，只需要少数几个能稳定拿到、类型有梯度的样本；但 Agent 侧的读取能力要能兼容用户可能带来的各种来源与格式，不能只认一种。可选来源、获取路线与选样梯度已单独成页，见 [textured_mass/](textured_mass/sources.md)。

用户可以通过开放城市数据、项目既有测绘成果或自行扫描重建的导出文件提供这种输入。例如 [OpenDroneMap 官方输出](https://docs.opendronemap.org/outputs/) 包含带纹理 OBJ 及对应图片。优先入口建议为单栋 GLB 或 OBJ+MTL+贴图包，附可用的单位、方向、位置及建筑用途；资料缺少时进入交互/假设分支。城市瓦片先通过选楼/裁剪形成单体输入，非目标楼体、地面与树木的分离属于输入准备，不生成环境 BIM；完整原件只保留作来源。不同地区的开放覆盖和采集质量有差异，不能承诺任意地址可直接下载。

另有一种更轻的来源是**带图片纹理的规则化建筑外壳**，不必都是密集摄影测量网格。[Helsinki 官方说明](https://www.hel.fi/en/decision-making/information-on-helsinki/maps-and-geospatial-data/helsinki-3d) 同时提供实景 OBJ 和带纹理的 LoD2 城市建筑模型；后者包含建筑对象身份，适合从单体层次组织输入。既有 BIM/CAD 导出的外壳也可进入同一输入类，但可见表面证据与原文件中已有语义应分别利用。

当前城市建模的常见基线可概括为建筑轮廓/高度/层数，加建筑用途、年代等信息，再赋典型参数与简化分区。界面上的体块不表示求解器内部完全没有窗、楼层或热区：

- [CEA 官方当前数据管理说明](https://github.com/architecture-building-systems/CityEnergyAnalyst/blob/master/docs/tutorials/cea4-app-training/08-data-management.md) 以用途、年代、建造标准及气候区映射典型围护、窗墙比、层高、内部负荷和系统信息。
- [URBANopt 基线](https://docs.urbanopt.net/resources/scenarios/baseline.html) 从 GeoJSON 拉伸建筑并派生核心/周边热区，可考虑邻楼遮阳，结合典型建筑构造、作息和系统。其 [映射接口](https://docs.urbanopt.net/resources/customization/modifying_mapper.html) 允许部分建筑使用详细 OpenStudio 模型，其他建筑继续默认生成。
- [UMI 能源模块](https://umidocs.readthedocs.io/en/latest/docs/energy-module-advanced.html) 使用代表性 shoebox 模型作为计算抽象。不能将所有城市模型统称为完全无细节体块，也不能假设增加源细节会自动穿透这些后端的简化。

这些资料支持的产品机会是：利用实际外壳、贴图与补充信息，减少单栋几何/开口对统一默认值的依赖，按用户选择的空间复杂度生成通用 BIM，再向后端交付。上面的模拟做法仅是背景，不定义本项目源空间划分，也不引入环境建模。现有详细模型接口说明存在对接路径，**本项目尚未实现 CEA、UMI 或 URBANopt 的适配**。

## 复杂度与空间块（用户确认）

**分块以实体隔墙形成的实际建筑空间为依据。复杂度表示：假设建筑信息已经完全推理准确，对这些空间做什么程度的简化/合并。** 这是定义复杂度的概念参照，生成时无需真的先推断完整建筑，也不引入评测 GT。各档都交付通用的空间块、边界、门窗/开口与关系。

简化较多时可合并若干实际空间、保留主要组成；简化较少时保留更多实际分隔与跨层差异。此前核心筒、走廊、四朝向办公室的描述仅为理解示例，不预设三档，不固定各档对应关系，也不将特定平面作为通用合并规则。

**若核心筒四周本来就是一圈开放办公，最细档也保持一个四周空间。** 不能因提高复杂度、不同朝向或不同功能而加源分界；同栋建筑在不同档位可能得到相同空间块数。此前的三档例子不是所有楼的固定切分模板。

这里的合并是通用源 BIM 对实际空间的简化，不能仅因外形类似热区划分就移交后端。一个粗块可以代表多个未展开的实际房间，不宣称其内部真的没有隔墙。物理隔断、抽象边界与未知状态仍需分别表达，但这种区分不授权在大开敞空间内凭空加分界。闭合用于界定空间范围与体积，不等于每张边界面都是实墙或实楼板。

低复杂度可直接生成粗空间方案，无需先完整推断逐间布局再合并。已有细致资料可保留在输入证据及抽象对应记录中，不要求低档输出全部细节；用户选择的简化必须可解释，不能静默漏掉已知对象再冒称逐间重建成功。环绕核心筒的四周块允许是非矩形、有内环的逻辑单元；若几何实现需分片，应保持一个源块身份，计算片间不增设物理墙。具体表示尚待实现，不据此声称现有单外环导出已支持。

建筑用途、层数、入口、窗排列和已知尺寸为推断实际分隔提供依据；模拟用途不决定生成档位。细档保留更多推断为实际存在的分隔，不能仅为达到块数目标造房间。生成过程中可交互补信息。复杂度决定简化/合并程度，准确性取决于证据和验证，两者分别报告。

### 09-16 内部假设复核与动态复杂度（澄清及助手建议）

用户指出候选内部基本整层开放，并询问是推理结论还是简化版本、是否需要先规定复杂度档位。核对[开发输入](../logs/experiments/2026-09-15_voimatalo_developer_walkthrough/building_input.json)与[方案脚本](../logs/experiments/2026-09-15_voimatalo_developer_walkthrough/prepare_case_plan.py)：输入原本要求有用、适度细致的办公/交通/服务空间推断；实际方案主动采用“每层连续L形开放办公/商业空间，加服务空间与连续交通核心”。这是一种开发助手选取的过粗布局假设，没有证据证明实际就是开放办公，也没有先完整推理逐间布局再合并，更不能解释为用户已选择低档。主体沿用了该假设，本程重点修外部开口、层界和屋顶，内部推理不足。不能以避免凭空拆已知开敞空间为理由，将未知内部默认成开敞空间。

用户强调有些建筑完整复原也很简单。这与既有“简化/合并程度”定义一致：建筑自身复杂程度、用户希望保留的空间细节、输入信息充分程度应分别描述。完整保留单厅仓库可能只有一个空间，完整保留酒店则可能有很多房间；同等保留意图不要求同等房间数，细节多也不代表证据充分。

助手建议先明确每案保留哪些实体分隔与空间关系、允许合并什么，再根据案例收敛通用档位；不必先规定固定三档、房间数或面积门槛。粗表达必须说明哪些内部细节没有展开，不能表示为“确认无墙”；需要补全的未知处仍应形成明确标注的合理假设。低档仍可直接推断合并后的表达，不增加先完整生成全楼的前置。具体档数、控件、局部配置及默认值尚未决定；此建议不视为用户已经确认新的产品规格。

## 生成组织与后端边界（方案建议）

建议依赖关系为：**单体输入 + 用户选择复杂度 → 外壳与楼层/开口观察 → 相应粒度的空间块方案 → 通用 BIM 生成与检查 → 查看/编辑 → 选择模拟插件 → 后端派生与调整**。用户未选择模拟也能完成 BIM 生成和交付。总 Agent 按当前信息选择查看、量测、类型假设、提问、生成与检查动作，可回看与局部修订；这不是固定串行 Agent 清单。生成中补信息与生成后的停点编辑分别处理。

类型规律可以作为先验和确定性几何工具，例如标准层重复、核心筒与走廊布置、窗与房间的相对约束。模型判断实际分隔、适用模式及例外，并按用户复杂度直接推断相应简化后的表达；代码求尺寸、排布与检查。开放办公本身是应保留的格局，不能强套逐间模板。外部观测和内部假设共同形成源 BIM，原始网格留作证据。

后端从该源 BIM 派生自身模型，可以进一步合并、细分、调整或补充。**源空间粒度和后端计算粒度是两项独立选择**；同一个简单档或复杂档 BIM 都可接不同插件，后端调整记录与源对象的对应关系，不静默覆盖共同底座。材料构造和运行参数沿用协作者模块。

后续评价可在同栋建筑、不同源复杂度上分别检查空间表达质量，再通过具体后端检验仿真改善。后端是否消费新增细节会影响结果，但不能反过来成为生成档位的定义或必填配置。当前不开展仿真，也不把细节数量当成精度提升证据。

### 09-16 视觉构件工具讨论（尚未选型或实施）

**收工决定覆盖下方先行评估建议：用户明确视觉模型暂缓，开发模型与用户一起调好验收，再迁移工作模型；迁移完成后根据实际问题决定是否补视觉等工具。本节只保留技术讨论，不是当前待执行任务。**

用户提出配置YOLO等视觉模型辅助门窗识别，作为工作模型工具。助手建议值得开展小范围效果评估，定位为可调用的感知能力：模型选择原网格观察，检测器给候选框/可选掩膜、类别分数及原视图，代码按相机/网格深度映射宿主并跨视图去重，工作模型判断、补缺和改源。检测分数不是“真实构件概率”，无检测也不等于无窗或透空。

起步可比较文本类别驱动的[Grounding DINO](https://github.com/IDEA-Research/GroundingDINO)与[YOLO-World](https://docs.ultralytics.com/models/yolo-world)，避免尚无代表标注时先投入专用训练；需要边界轮廓时再接[SAM 2](https://github.com/facebookresearch/sam2)，不将分割工具当建筑语义或补全模型。固定构件类别和代表数据成熟后可评估[专用YOLO微调](https://docs.ultralytics.com/guides/finetuning-guide)。这是技术建议，不是用户已确定的型号、训练预算或部署任务。

评估应使用本项目真实纹理视图及独立建筑，按楼栋隔离训练/验证，明确窗洞、玻璃分格、门等标注粒度；看漏检、误检、重复/错并窗、完整尺寸、宿主对应和实际BIM收益，不能只看通用榜单或框数。图纸符号与实景纹理分开验证。低清/拉伸/阴影/缺面域上的效果尚未实测。

视觉工具不能独立决定不可见的内部隔墙、交通核心或缺失体量。当前开发候选仍须先修内部空间组织与缺失补全并经用户验收，不能用安装检测器或标注未知替代建模任务。

## 调研结论

**09-20 接手复核：先验证完整转换和实际可读性。** 香港15例原转换全批丢轴向节点，两例还漏62面；已从原件重新无损打包全部场景，完成离线四视图，当前2例优先复核用途/关键立面。旧单层/高层及高/中/低质量标签未成立，不能按下载量或格式通过验收素材。见[完整素材入口](../../case_tests/textured_mass/hongkong/README.md)和[来源复核](../logs/experiments/2026-09-20_hongkong_material_audit/source_review.md)。

09-18的来源/获取/复杂度/格式调研分别保留在[textured_mass/](textured_mass/sources.md)，其中来源、获取与梯度本轮已纠偏；格式兼容表仍是开发调研，不代表全部格式已有生产实现或整案实测。来源是否带真实贴图、转换是否完整、立面是否可读应分别核实，不能由CityGML/GLB文件名或格式加载通过推定。

现有输入生成能力和未支持边界以[实现说明](implementation.md)及实际代码为准。公开IFC外壳作为合成输入已由用户登记为待议路径，本轮不展开；它可提供一种已知几何对照，但不是唯一评价办法，仍需核对具体资产内容与许可。

**能先拿到案例，并开展有边界的体量到 BIM 实验。** 当前已下载三个真实城市片区，加载几何与纹理、生成纯输入副本及预览；不能据此声称内部推断或 BIM 生成已跑通。当前可复用源 BIM、确定性几何工具和查看机制，新工作主要在体量读取、视图与空间位置对应、外壳语义及内部假设。

已有外部几何会减少外形、比例和视角对齐的推断，但它可能有噪声、缺面、植被与建筑粘连。窗常在图片贴图上比在三角面形状上更清楚；网格可渲染并不意味着是闭合建筑，更不意味着已有楼层、门窗或空间关系。

## 首例怎样接现有产品

以下是实施建议，尚未固定为所有输入必须遵循的流水线：

1. **确定建筑范围与可用几何。** 先选择一个主体较完整、用途符合范围的单栋；记录选择范围、坐标变换、单位依据和缺面。移除非目标对象属于输入准备，不重建周边环境。计算截面、拟合主要墙/屋面等由代码工具完成，保留未规整原件供比较。不要求先修成完美闭合网格。
2. **让模型看贴图并取得空间位置。** 工具可提供整体、局部与立面方向视图，同时保留相机参数、深度/面 ID，支持图像点回到三维表面。纹理图集本身常被切碎，不宜只把图集当平面建筑图阅读。模型识别楼层、窗、门、阳台，代码执行投影、尺寸计算和宿主关系检查。
3. **按用户复杂度补内部。** 在外壳与楼层约束下，结合建筑用途、入口、进深和窗排列提出相应粒度的空间块方案。需要时询问用途、层数或已知尺寸；回答细化当前假设，能先推进的部分继续。粗块不必先推断每间房，细档也不能把窗数直接等同于房间数；推断隔墙与抽象分界分别说明。
4. **形成共同 BIM 并回看。** 共用源空间、边界、开口与连接，保留每项来源。由代码检查相交、越界、宿主、实际连通及主要外形一致性；总 Agent 可根据图像/几何反馈选择局部修订。当前源方案导出主要覆盖正交多边形，非正交墙、复杂屋顶等需要按首例实际范围接入，不能先声明任意实景网格可用。

**案例建议已随用户范围调整：** 三片 SUM 数据保留为素材池，先核实普通办公、住宿或商业用途及单栋边界，再选择首例。此前仅依据独立外形推荐 `Tile_+1985_+2693` 中主体的标准不足，不再默认指定；用途未核实的独立主体或复杂公共建筑不优先。之后再按需要选择带内院或有遮挡的单栋样例。开发助手选目标须记为输入准备，不能把评测标签帮助裁楼或内部答案输入后的结果报告为完全自动冷启动。
